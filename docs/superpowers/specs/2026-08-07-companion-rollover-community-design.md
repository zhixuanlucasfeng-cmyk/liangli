# 伙伴动画、每日换日与校园社区设计

日期：2026-08-07  
状态：已批准，待实现计划  
目标版本：Liangli 下一阶段版本

## 1. 背景与问题

当前版本已经具备 Power 猫与人形 Power 的四态视频伙伴，但视频是从单张 WebP 海报通过局部网格形变生成的。虽然编码和循环连续性合格，实际观感仍接近整张画面周期性放大缩小，不像角色在表演。视频海报的固有背景与页面舞台渐变也不完全一致，产生可见色块。

当前跨天逻辑存在三个边界问题：日期来自 `toISOString()` 的 UTC 日期；只在页面加载时执行；昨天未完成的任务继续留在今日列表并占用精力。这不满足“用户当地时间每天重新开始”的产品语义。

用户还要求新增账号、好友聊天与类似校园墙的社区。该能力需要后端、身份认证、实时数据、内容安全与隐私权限，因此将项目扩展为“本地成长工具 + 可选联网社区”，但不把个人任务、心情和专注数据上传到云端。

## 2. 设计原则

1. 私密成长数据继续本地优先，注册账号不是使用五个成长模块的前提。
2. 每个本地日历日都是新的精力周期；昨日未完成事项保留，但不制造今天的负担。
3. 伙伴动作必须来自角色身体部位和姿态变化，禁止用镜头推拉或整图缩放冒充动作。
4. 社区采用半匿名展示、后台可追溯和最小权限访问，不提供完全匿名且无法追责的发布。
5. 维持纯前端 PWA 与 GitHub Pages 部署；联网功能通过 Supabase 托管服务提供。

## 3. 范围拆分与实施顺序

本次需求分成三个可独立验收的子项目，按以下顺序实施：

1. **每日换日**：修正本地日期、跨午夜检测和任务迁移，先确保核心产品逻辑正确。
2. **伙伴动画与舞台**：替换 8 段素材并统一舞台色，解决最明显的视觉问题。
3. **账号、好友私聊与校园墙**：引入 Supabase、社区界面和安全规则。

前两项不依赖联网配置，可以独立上线。第三项只有在 Supabase 项目 URL、匿名公钥和数据库迁移可用后才启用；配置缺失时入口显示清晰的“社区暂未开放”，不能影响本地功能。

## 4. 每日换日设计

### 4.1 本地日期键

新增 `localDayKey(date = new Date())`，使用设备本地的 `getFullYear()`、`getMonth()`、`getDate()` 生成 `YYYY-MM-DD`。不再使用 UTC `toISOString()` 作为“今天”。

### 4.2 任务归属

新任务增加 `dayKey`。读取旧任务时，缺少 `dayKey` 的记录视为当前迁移日的任务，保证旧用户数据不丢失。

今日页只展示 `dayKey === currentDayKey` 的任务，精力负荷也只统计这些任务中的未完成项。

### 4.3 换日行为

检测到日期变化时：

- 昨日未完成任务转成成长池想法，保留名称和原精力值，并记录来源日期；
- 昨日已完成任务进入本地任务历史，不再显示在今日列表；
- 今日专注分钟和番茄次数归零，周趋势按实际跨越天数推进；
- 更新 `lastDay`，重新渲染今日、成长池和专注统计；
- 显示一次温和提示：“新的一天，精力已经重新归零。昨天没做完的事放回成长池了。”

### 4.4 检查时机

换日检查在以下时机执行：

- App 启动；
- 页面从后台恢复时的 `visibilitychange`；
- 窗口重新获得焦点；
- 指向下一个本地午夜的定时器触发。

每次检查后重新计算下一个午夜，覆盖设备休眠和时区变化场景。

## 5. 伙伴动画与舞台设计

### 5.1 素材规格

继续保留两个角色和四个状态，路径保持 `assets/power-{cat|human}/{state}.mp4`，避免改动状态切换接口。

| 项目 | 规格 |
|---|---|
| 数量 | 8 段 MP4 + 8 张 WebP poster |
| 尺寸 | 512×512 |
| 时长 | 2–4 秒 |
| 帧率 | 30fps |
| 编码 | H.264 / yuv420p / 无音轨 |
| 镜头 | 固定，不推拉、不摇移 |
| 背景 | 精确纯色 `#0b0c0f` |
| 循环 | 首尾姿态、光线和背景连续 |
| 体积 | 单段目标不超过 700KB，8 段总计不超过 5MB |

### 5.2 状态表演

- `idle`：呼吸、眨眼；猫尾或头发轻微跟随摆动。
- `content`：身体主动前倾、得意表情、小幅姿态变化；衣服和头发有次级动作。
- `tired`：肩膀下沉、慢眨眼或短促打哈欠；节奏变慢。
- `exhausted`：满足地躺平睡觉，以缓慢呼吸循环；不能像受伤、被击败或痛苦。

动作验收要求至少有两个相对独立的身体区域产生不同运动轨迹，并且角色重心或关节姿态发生可感知变化。仅有统一缩放、统一平移或局部橡皮形变均判定不合格。

### 5.3 播放与背景融合

保留现有双 video 预加载与交叉淡入、poster 兜底、`prefers-reduced-motion` 静态降级和运行时视频缓存。

舞台背景改为同一个 CSS 变量 `--companion-bg: #0b0c0f`；素材生成、poster、video 容器和视频加载失败兜底全部使用该变量对应的确定颜色。视频不再叠加会改变背景观感的整体 `filter`。

## 6. 账号与社区架构

### 6.1 产品入口

现有五个底部页面保持不变。Header 新增“校园”入口，打开独立的全屏社区层，内部包含：

- 校园墙；
- 消息；
- 我的。

关闭社区层后返回原来的本地页面和滚动位置。

### 6.2 身份与资料

Supabase Auth 提供邮箱 + 密码注册、登录、退出和重置密码。注册后创建 `profiles` 记录，包含昵称、头像、唯一邀请码、账号状态和创建时间。

校园墙对其他用户只显示昵称和头像，不展示邮箱或真实姓名。服务端仍保存作者账号 ID，以支持权限、举报和封禁。

### 6.3 好友与私聊

用户通过邀请码发起好友请求。接收方同意后形成双向好友关系；拒绝不会暴露额外账号信息。

只有已接受的好友能创建或读取双方的一对一会话。消息支持文本，第一版不支持图片、文件、群聊、已读回执或消息撤回，以控制范围和安全风险。

拉黑后双方不能再发送新消息、发起好友请求或看到彼此的校园墙内容。

### 6.4 校园墙

第一版支持：

- 发布和删除自己的纯文字帖子；
- 评论和删除自己的评论；
- 每个账号对帖子点赞或取消点赞；
- 举报帖子或评论；
- 拉黑用户；
- 按最新发布时间分页加载。

第一版不支持图片、视频、定位、真实学校认证、私信陌生人、热门算法或完全匿名发布。

### 6.5 数据模型

核心表：

- `profiles(id, display_name, avatar_url, invite_code, status, created_at)`
- `friend_requests(id, sender_id, receiver_id, status, created_at)`
- `friendships(user_id, friend_id, created_at)`
- `conversations(id, created_at)`
- `conversation_members(conversation_id, user_id)`
- `messages(id, conversation_id, sender_id, body, created_at)`
- `wall_posts(id, author_id, body, created_at, deleted_at)`
- `wall_comments(id, post_id, author_id, body, created_at, deleted_at)`
- `wall_likes(post_id, user_id, created_at)`
- `reports(id, reporter_id, target_type, target_id, reason, status, created_at)`
- `blocks(blocker_id, blocked_id, created_at)`

所有时间由数据库写入 UTC；前端仅在显示时转为设备本地时间。

### 6.6 权限与安全

所有社区表开启 Supabase Row Level Security：

- 用户只能修改自己的 profile；
- 私聊内容只允许会话成员读取，且发送者必须是当前用户；
- 会话创建必须对应已接受的好友关系；
- 用户只能删除自己的帖子和评论；
- 举报只有举报者和管理员能读取；
- block 规则优先于好友、墙和消息查询；
- 前端使用 Supabase 匿名公钥，绝不包含 service-role key。

帖子、评论和消息在客户端与数据库约束层限制长度，按账号限制发布频率。正文始终作为文本渲染，禁止注入 HTML。

## 7. 数据流与离线行为

本地五页继续通过现有 `DB` 封装访问 `localStorage`。Supabase 客户端只服务社区模块，两类数据不混存。

校园墙使用分页查询；好友请求和私聊消息使用 Supabase Realtime 订阅。网络断开时社区显示离线状态和最近一次内存缓存，不伪装发送成功。重新联网后用户可以手动重试失败消息；第一版不做后台离线发送队列。

Service Worker 只缓存社区 UI 壳和静态资源，不缓存带身份信息的 Supabase API 响应。

## 8. UI 与可访问性

社区延续荒诞漫画语言，但功能区域保持稳定：

- 校园墙使用撕纸公告栏卡片；
- 消息使用漫画对话框；
- 表单、举报、拉黑和登录区域保持规整，不使用影响点击和阅读的不规则旋转；
- 所有图标按钮有文字或可访问名称；
- 键盘可以完成注册、发帖、评论、加好友和发消息；
- 点赞、好友状态、发送失败不能只依靠颜色表达；
- 中英文文案同时提供。

## 9. 错误处理

- Supabase 未配置：本地五页正常使用，社区入口显示未开放状态。
- 注册或登录失败：显示可理解的本地化错误，不展示原始服务错误或堆栈。
- 重复邀请码、重复好友请求和重复点赞：由唯一约束保证幂等，前端同步最终状态。
- Realtime 中断：显示“正在重新连接”，恢复后重新拉取会话最新消息，避免漏消息。
- 发布频率过高或正文超限：拒绝提交并保留用户已输入的正文。
- 被拉黑、内容被删除或账号被停用：返回统一不可用状态，不泄露额外账号信息。

## 10. 测试与验收

### 10.1 每日换日

- 覆盖中国时区、UTC 前后日期不同、跨午夜、后台休眠后恢复和手动修改时区；
- 验证昨日未完成任务只迁移一次，成长池无重复记录；
- 验证今日负荷从 0 开始，旧格式 localStorage 数据兼容；
- 验证多日未打开时周趋势推进正确。

### 10.2 伙伴动画

- 用 `ffprobe` 验证 8 段编码、尺寸、帧率、时长、音轨和体积；
- 连续解码并循环至少 5 次，确认无黑帧、跳帧和首尾跳变；
- 运动检测确认不是全画面统一缩放，并由人工检查关节、表情和次级动作；
- 在 375、390、440 CSS 像素宽度和 iOS/Android 自动播放策略下验证；
- 验证视频边缘与舞台背景不存在肉眼可见色块。

### 10.3 社区

- 两个普通账号覆盖注册、登录、邀请码好友请求、接受、私聊和退出；
- 第三个非好友账号不能读取私聊或直接发消息；
- 覆盖发帖、评论、点赞、举报、删除自己内容和拉黑；
- 直接调用 API 验证 RLS，不能只测试前端隐藏；
- 覆盖断网、Realtime 重连、重复提交、超长文本和快速连续发布；
- 验证未登录和 Supabase 未配置时本地五页不受影响。

## 11. 非目标

- 本阶段不把任务、目标、心情或专注数据同步到账号；
- 不做陌生人私信、群聊、图片消息、语音、视频通话；
- 不做图片或视频校园墙；
- 不做学校实名验证、位置服务或推荐算法；
- 不建立自托管服务器，也不把 Supabase service-role key 放进客户端。

## 12. 发布策略

三个子项目分别通过测试后提交。每日换日和伙伴动画可以先部署。社区使用配置开关，在数据库迁移、RLS 自动化测试和生产环境变量全部就绪后才开放入口。

Service Worker 每次静态资源或素材变更都升级缓存版本。发布后验证 GitHub Pages 在线更新、PWA 离线核心功能、社区登录和两账号端到端消息流。

## 13. 自检记录

- 文档不含 TBD、TODO 或未决定的交互分支。
- 核心本地数据与联网社区数据边界明确，注册不会隐式上传私人记录。
- 每日换日使用本地日历日；云端社区时间使用 UTC，两者用途不同且不冲突。
- 拉黑、好友关系、会话权限和 RLS 的优先级一致。
- 社区第一版明确排除媒体、群聊和陌生人私信，范围可在单独实施计划中拆分。
- 动画背景颜色、CSS 舞台颜色和失败兜底颜色统一为 `#0b0c0f`。

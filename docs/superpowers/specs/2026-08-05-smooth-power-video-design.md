# 丝滑 Power 伙伴视频重制 设计文档

日期：2026-08-05
状态：已批准，待写实现计划
范围：仅动画素材规格与播放性能架构。不改产品代码、不改现有素材文件、不改负荷阈值逻辑。

## 背景 / 问题

`量力 Liangli` 现在的 Power 伙伴（Power 猫 / 粉发人形 Power）已经是视频驱动的四态角色（`idle`/`content`/`tired`/`exhausted`），实现见 `index.html` 的 `companionVideoSrc()`/`renderCompanion()` 和单个 `<video id="companionVideo">` 元素，素材在 `assets/power-cat/` 与 `assets/power-human/` 下，共 8 个 `.mp4` 文件（每个约 60-84KB）。

当前实现有两类卡顿，是这次要解决的问题：

1. **持续播放卡顿**：单段视频循环播放到结尾再从头开始时，如果视频本身不是严格无缝循环（首尾帧动作/光照不连续），会有肉眼可见的跳变感。
2. **状态/角色切换卡顿**：切换负荷状态（如 `content`→`tired`）或切换角色（猫↔人形）时，现在的实现是直接把同一个 `<video>` 元素的 `src` 换掉，浏览器需要重新请求、解码、起播，中间会有一段黑屏/卡顿。

这份文档只解决这两类卡顿，用「新素材规格」+「双层播放架构」共同实现。**不涉及**：负荷阈值改动（沿用 `renderLoad()` 现有的 80%/100% 分界）、新增后端、引入构建工具/npm/前端框架——这些都违反项目 CLAUDE.md 的技术约定。

## 目标

1. 用 8 段全新录制/渲染的连续动画替换现有 8 个视频文件，从素材层面消除首尾不连续导致的循环跳变
2. 用双层 `<video>` 交叉淡入架构替换现在的单层切换，消除状态切换和角色切换时的黑屏/卡顿
3. 保留现有产品行为不变：Power 猫、粉发人形 Power 两个角色；`idle`/`content`/`tired`/`exhausted` 四态；中英双语文案；用户选择的角色持久化在 `localStorage`（`DB.get('companion', 'cat')`）
4. 首次加载和弱网/离线场景下体验不劣化于现状

## 非目标（这次明确不做）

- 不新增角色、不新增状态
- 不改变 `renderLoad()` 里负荷比例到状态名的映射规则
- 不引入云端渲染服务或后端接口
- 不引入 React/Vue 等前端框架，不引入 npm 构建链
- 不做视频内嵌音效/配乐（保持无音轨，和现状一致）
- 不做用户可自定义素材/上传素材的功能

## 设计

### 1. 新素材规格（8 段）

替换对象：`assets/power-cat/{idle,content,tired,exhausted}.mp4`、`assets/power-human/{idle,content,tired,exhausted}.mp4`，共 8 个文件，文件名和目录结构不变（只替换文件内容），保证 `companionVideoSrc()` 的路径拼接逻辑不需要改动。

统一技术规格：

| 项目 | 规格 |
|---|---|
| 分辨率 | 512×512（正方形，与现有 `.companion-stage video { object-fit:contain }` 的显示框匹配） |
| 时长 | 2-3 秒 |
| 帧率 | 30fps |
| 编码 | H.264（AVC） |
| 封装 | MP4 |
| 像素格式 | yuv420p（保证移动端 Safari/Chrome 硬解兼容） |
| 音轨 | 无（不封装音频流，不是静音音轨） |
| 背景色 | `#191c22`（与 `.companion-stage` 当前背景色 `var(--card2)` 视觉一致，避免视频边缘与容器背景出现色差色块） |
| 循环方式 | 无缝循环——首帧与尾帧的角色姿态、光照、构图必须能直接衔接，中间不插入黑场/淡入淡出 |

体积预算：

- 单段文件建议 ≤350KB（在 2-3 秒、512×512、30fps 规格下，H.264 中高压缩率可达到）
- 8 段总计 ≤3MB（与现有 8 个文件约 480KB 总量相比留了充分余量，用于换取更高的动作质量和更长的首尾衔接缓冲）

### 2. 动画原则

这一节约束「怎么画/怎么拍这 8 段动画」，避免规格达标但观感变差：

- **动作幅度适中**：不要大开大合的动作（不要挥手到画面外、不要镜头推拉），角色主体应始终留在 512×512 画框内且不裁切
- **轮廓与五官稳定**：角色的外轮廓线条、眼睛/耳朵等五官定位在动画过程中不漂移、不抖动——这是判断"是否 AI 补帧形变"的关键指标
- **避免 AI 补帧形变伪影**：如果动画素材来自 AI 视频生成/补帧工具，生成后必须逐帧或抽帧检查，排除常见瑕疵：肢体融合、多余肢体、边缘闪烁、纹理漂移。有瑕疵的素材不可用，需重新生成或重新录制
- **`exhausted`（精疲力尽）态的情绪基调**：必须是「满足地躺平休息」——呼吸均匀、表情放松/闭眼，类似伸懒腰后躺下的状态。**不可以**表现为受伤、被打败、痛苦、皱眉、哭脸等负面情绪。这条继承自项目 CLAUDE.md 的产品红线：「超载时提醒，不阻止」「不制造新的焦虑」——伙伴的精疲力尽是「他也需要休息」的共情表达，不是对用户超载行为的负面评价或惩罚感

### 3. 播放架构：双层 video 交叉淡入

替换现有单个 `<video id="companionVideo">` 为两层叠放的 `<video>` 元素（同一个 `.companion-stage` 容器内，`position:absolute` 叠放，`object-fit:contain` 保持不变）。

状态机（每层维护「当前显示」或「预备」两种角色）：

1. **当前层播放**：可见层始终处于播放状态（`autoplay muted loop playsinline`），用户在这一层上看到当前角色+当前状态的动画持续循环
2. **下一层隐藏预加载**：当目标 `src`（角色或状态变化后应该显示的视频）确定后，把下一层的 `src` 设置为目标视频，该层此时 `opacity:0`（不可见）但已经在解码/预加载
3. **`canplay` 后延迟交叉淡入**：监听下一层的 `canplay` 事件，事件触发后等待约 150ms（给解码器留出稳定输出首帧的余量，避免过早淡入时露出黑帧/花屏），然后用 CSS `transition:opacity .25s ease`（沿用现有 `.companion-stage video` 已声明的过渡时长）把下一层淡入到 `opacity:1`，当前层同步淡出到 `opacity:0`
4. **切换完成后释放旧层**：淡入淡出的过渡结束后（可用 `transitionend` 事件或与过渡时长匹配的定时器），把原「当前层」暂停（`pause()`）并清空其 `src`（释放解码器资源），角色互换——刚淡入的层成为新的「当前层」，旧层成为下一次切换时可复用的「预备层」
5. **并发解码上限**：任意时刻最多只有两层在解码（当前层 + 正在预备的下一层），不会同时存在三段及以上视频解码，避免低性能设备资源耗尽

这套架构解决切换卡顿的关键在于：**用户看到的从始至终都是一段正在播放的视频**，只是底下悄悄换了一层——不存在「旧视频停止→新视频从零开始加载」这段空窗期。

### 4. Poster 兜底

为 8 段视频各配一张对应的 WebP 静态海报图（`assets/power-cat/idle.webp` 等，与视频同目录同名不同后缀），显示时机：

- 视频层的 `src` 已设置但尚未触发 `canplay`（网络慢、首次加载）时，该层用 `poster` 属性显示对应海报，避免黑屏
- `prefers-reduced-motion: reduce` 时（见第 7 节），直接常驻显示海报，不请求视频
- 海报内容取对应视频的首帧或最具代表性的一帧，构图与视频一致，避免"海报到视频"切换时出现跳变感

### 5. 加载与缓存策略

- **首次加载**：只请求当前应显示的 1 个视频文件 + 其对应 poster，不预取其余 7 个视频。这保证首屏加载量最小，和现有单文件架构一致
- **空闲预加载**：页面空闲时（用 `requestIdleCallback`，不支持则退化为 `setTimeout` 延迟执行），预加载**同一角色**、**高概率会切换到**的下一状态视频——例如当前 `content`，负荷会自然地涨向 `tired` 而不会跳到 `idle`，所以优先预取 `tired`；不预取另一个角色的视频（角色切换概率低于状态切换，且用户未必会切换角色）
- **Service Worker 精确分层缓存**：
  - **安装期（`install` 事件）精确缓存 8 张 poster**：体积小、必须保证离线可见，纳入 `sw.js` 的预缓存清单
  - **MP4 运行时按需缓存**（沿用现有网络优先/离线回落策略）：不在 `install` 阶段预缓存全部 8 个视频（体积和加载时间都不划算），而是用户实际播放到某段视频时，运行时经过 fetch 事件顺带写入缓存，下次离线访问时命中
- **缓存版本号**：本次改动替换了 8 个 MP4 文件内容（文件名不变），必须让旧版 Service Worker 缓存失效，否则用户拿到的还是旧素材。按 CLAUDE.md 约定，`sw.js` 的 `VERSION` 常量需要 +1（当前是 `liangli-v4`，改为 `liangli-v5`），并同步扩充预缓存清单以包含新增的 8 张 poster

### 6. 降级与容错

- 视频元素统一保持 `muted autoplay loop playsinline` 四个属性——这是让移动端 Safari/Chrome 允许自动播放的必要组合，任何一个缺失都可能导致自动播放被浏览器拒绝
- **`autoplay` 失败兜底**：监听 `play()` 返回的 Promise，若 reject（浏览器拒绝自动播放），该层保持显示其 `poster`，不留黑屏，也不重试播放骚扰用户
- **`prefers-reduced-motion: reduce` 用户**：直接不加载/不播放任何视频，两层 `<video>` 常驻显示各自状态的 poster，状态切换时只切换 poster 图（走现有 `.companion-stage video` 的 `opacity` 过渡，无需播放逻辑），尊重用户的系统级动效偏好
- **低性能设备**：不长期维持双层同时解码——第 3 节的双层解码只在「切换过渡进行中」这个短暂窗口内存在（过渡结束后旧层立即释放），稳定态永远只有 1 层在解码，和现状的资源占用量级一致

### 7. 状态数据流

沿用现有数据流，不新增字段：

- 角色选择：`S.companion`（`'cat'` | `'human'`），来源 `DB.get('companion','cat')`，写入走 `DB.set`，不直接调 `localStorage`（遵守 CLAUDE.md 约定）
- 状态计算：沿用 `renderLoad()` 里已有的 `used`/`max` 比例推导出的状态字符串（`idle`/`content`/`tired`/`exhausted`），伙伴状态永远是任务数据的纯派生值，刷新页面自动重新计算
- 视频/海报路径：`companionVideoSrc(companion, state)` 的拼接逻辑不变（`assets/power-${companion}/${state}.mp4`），新增一个同构的 poster 路径函数返回 `.webp` 版本
- 双层切换只是 `renderCompanion()` 内部的播放层管理逻辑变化，不引入新的全局状态字段

### 8. 错误处理

- 视频加载失败（`error` 事件，例如离线且未命中缓存）：该层回退显示 poster；若 poster 也不可用（理论上不会发生，因为 poster 已被 Service Worker 精确预缓存），回退为容器背景色纯色块，不抛出未捕获异常、不在界面上出现破损图标
- 双层切换逻辑中的定时器/事件监听需要在组件重新调用 `setCompanion`/状态变化时清理旧的监听器和定时器，避免快速连续切换（用户连点角色按钮）时出现多个交叉淡入过程互相覆盖导致的闪烁或播放层状态错乱

## 9. 可访问性

- 两层 `<video>` 元素保持现有的 `aria-hidden="true"`（伙伴是纯装饰性视觉反馈，不承载必须由屏幕阅读器读出的信息，语义仍由旁边的负荷数字/进度条承担）
- 角色选择按钮（`.companion-picker button`）保留现有 `aria-pressed` 状态同步逻辑，双层切换过程不影响按钮的可访问性属性
- `prefers-reduced-motion` 的降级路径（第 6 节）本身就是可访问性要求的一部分，不是可选项

## 验收标准

实现完成后，按以下清单逐项验证（本项目无自动化测试基础设施，沿用手动验证方式）：

1. **媒体规格核验**：用 `ffprobe` 逐一核对 8 个新 MP4 文件的分辨率（512×512）、时长（2-3s）、帧率（30fps）、编码（H.264/AVC）、像素格式（yuv420p）、音轨（无）；核对文件体积（单段 ≤350KB，8 段总计 ≤3MB）
2. **循环解码检查**：每段视频至少连续循环播放 5 次，逐次观察循环点（尾帧→首帧衔接处），确认无跳变、无黑场闪烁
3. **移动端验证**：在真实移动设备或浏览器移动 viewport 模式下验证自动播放正常触发、`playsinline` 生效（不会被拉去全屏播放器）
4. **持续播放顺滑度**：任一角色任一状态静置播放 30 秒以上，确认循环点不可察觉
5. **切换无黑帧**：连续切换状态（模拟负荷从 0 推高到超过 100%，触发 idle→content→tired→exhausted 全部路径）和连续切换角色（猫↔人形），确认过渡期间没有黑屏、没有花屏、没有明显卡顿
6. **刷新记忆**：选择某一角色后刷新页面，确认 `S.companion` 从 `localStorage` 正确恢复，显示的仍是用户上次选择的角色
7. **离线回访**：本地服务下先完整加载一次页面（触发 Service Worker 安装与运行时缓存），断网后刷新页面，确认 poster 立即可见、已缓存过的视频可正常播放、未缓存的视频优雅回退到 poster 而非报错
8. **中英文标签**：切换页面语言，确认角色名称（`companionCat`/`companionHuman`）等相关文案两侧 key 一一对应，视频/海报显示不受语言切换影响
9. **控制台无错误**：完成上述所有操作后检查浏览器开发者工具控制台，确认没有出现未捕获的 JS 异常或视频相关的 warning/error

## 范围边界重申

- 不改动 `renderLoad()` 的负荷阈值（80%/100% 分界线）——这属于产品逻辑，不属于本次动画性能改动范围
- 不引入任何后端服务或云端接口
- 不引入前端框架或 npm 构建工具链，双层播放架构用原生 `<video>` + CSS `transition` + 原生 JS 事件监听实现，写在现有 `index.html` 的 `<script>` 段内
- 不修改现有的 8 个素材文件路径命名规则和目录结构，只替换文件内容并新增 8 张同名 poster

## 自检记录

- 文档不含 `TBD`/`TODO` 占位符，所有数值型规格（分辨率/时长/帧率/编码/体积/延迟毫秒数等）均已给出具体值
- 第 1 节素材规格与第 6 节降级策略之间无冲突：`muted autoplay loop playsinline` 是播放层的通用属性设置，不受视频本身规格影响
